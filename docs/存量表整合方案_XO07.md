## 二、整合实施顺序（建议）

1. **P1 通知双轨合并**（✅ 已实施）：`sys_notifications` 五个端点全部切至 `task_notifications`（`source='app'` 区分，`client_ref` 部分唯一索引保幂等）；读路径双读（新表 UNION 旧表未并入行），写路径只写新表；旧表只读保留 30 天后废弃。存储层实现集中在 `server/modules/notifications/notify.js`。
2. **P2 权限表收敛**（✅ 已实施）：`sys_skill_permissions` → `skill_permissions`（新架构命名，去 sys_ 前缀）；启动期幂等建表 + 一次性回填（ON CONFLICT 幂等可重跑）+ 新表未命中双读旧表兜底；写路径只写新表。切换面仅 `skillPermissionStore.js` 门面一处，evaluator/permissionRoutes 零改动。旧表只读保留 30 天后废弃。
3. **P3 用户身份迁移**（✅ 已实施，单租户平移）：根因修复——`sys_users`/`sys_roles` 为全库 FK 与权限判定根基但仓库从未有建表 DDL（历史手工表），已在 `runInitDDL` 补齐 CREATE TABLE（全新环境自洽）+ 存量库幂等 `ADD COLUMN IF NOT EXISTS` 列对齐（display_name/email/role/is_active/avatar_url/last_login_at + roles 的 permissions/is_builtin/display_name）。角色技能授权已由 P2 `skill_permissions` 承接，不再另建无前缀副本表（避免冗余）。
4. **P4 mock 域合并**：纯收益无风险，随时可做。

## 三、D2 多租户决策（✅ 已定案：单租户强化）

**定案时间**：2026-09-19 ｜ **决策依据**：商业模式为「系统 + 本地化部署硬盘设备」打包售卖（appliance 一体机模式），每客户一台设备 = 整套系统 + 数据库实例级物理隔离。

| 决策 | P3 影响面 | 额外成本 |
|---|---|---|
| **单租户**（✅ 定案） | 三表平移 + 加新字段即可 | ~1-2 人日 |
| ~~真多租户~~ | （已排除）46 张表加 `tenant_id` + RLS；+15-25 人日 | 不做 |

**定案理由（appliance 模式 vs 多租户四目标）**：

| 多租户目标 | appliance 模式下 | 结论 |
|---|---|---|
| 数据隔离 | 每客户整套系统+库物理隔离在设备内 | 天然满足（比 RLS 更硬） |
| 统一升级 | 设备级版本管理（升级包/镜像） | 是设备运维问题，非租户问题 |
| 按租户计费 | 按设备售卖/授权，设备即计费单元 | 许可证解决（D5 专项，暂搁置） |
| 配置/品牌隔离 | 每台设备即该客户 | 天然满足 |

**衍生约定**：
- 全部 46 张表**不加** `tenant_id`、不引入 RLS；同一大客户内部多部门隔离用「工作区/组织」（sys_users/sys_roles 扩展）解决，不上升为租户架构。
- **D5 设备许可证与激活专项**（设备指纹 + 离线 license）：暂不考虑，待售卖临近再立项。

## 四、安全边界

- 所有迁移脚本将采用「新建→回填→双读校验→切读→停写→废弃」六步，每步可回滚
- 本轮**未执行任何 DDL/DML**——生产数据操作待老大确认方案后实施
